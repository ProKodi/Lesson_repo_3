# Конспект: Раздел 4. Приложения

## 4.1. Карьера тестировщика

Автор показывает развитие специалиста по тестированию как последовательное приобретение знаний и практических навыков.

### 1. Базовая подготовка

На начальном этапе необходимо освоить:

* основы тестирования;
* анализ документации и требований;
* разработку тестов и тестовых сценариев;
* поиск и документирование дефектов;
* составление отчётов;
* основные виды и методы тестирования;
* работу с компьютером и офисными программами;
* английский язык для чтения технической документации.

Также полезны базовые знания операционных систем, сетей, баз данных и SQL. ([FlipHTML5][2])

### 2. Функциональное тестирование

После базовой подготовки специалист углубляется в функциональное тестирование.

Основные навыки:

* создание чек-листов;
* разработка тест-кейсов;
* проведение функционального и доменного тестирования;
* поиск и описание дефектов;
* работа с системами управления тестированием;
* работа с баг-трекинговыми системами;
* оценка трудозатрат;
* планирование своей работы.

Автор указывает, что получение полного набора необходимых навыков для начала работы тестировщиком требует продолжительной практики. ([FlipHTML5][2])

### 3. Автоматизация тестирования

Следующий этап — автоматизация.

Для неё требуются:

* уверенные знания программирования;
* понимание принципов работы программ;
* знание инструментов автоматизации;
* умение выбирать подходящие технологии;
* создание и оптимизация автоматизированных тестов.

В качестве примеров технологий и инструментов в книге упоминаются **Java, C#, Python, JavaScript, SQL, Selenium, JUnit, NUnit, TestNG, Cucumber** и другие. ([FlipHTML5][2])

### 4. Дальнейшее развитие

После получения опыта специалист может развиваться в разных направлениях:

* **экспертное/техническое направление**;
* **управление проектами**;
* **управление ресурсами**;
* развитие в смежных областях, например бизнес-анализе.

Таким образом, карьера тестировщика не ограничивается только выполнением функциональных проверок. ([FlipHTML5][2])

# 4.2. Комментарии к заданиям

Этот подраздел содержит пояснения и решения к практическим заданиям из предыдущих глав книги.

Его задача — помочь читателю **проверить собственные рассуждения**, а не просто получить готовые ответы. Автор обращает внимание на типичные ошибки и показывает, как анализировать полученные результаты. ([studylib.net][1])

Основные идеи:

* после выполнения задания необходимо самостоятельно проверить результат;
* ошибки следует анализировать, а не просто исправлять;
* при тестировании требований важно учитывать как интересы заказчика, так и возможность реализации и проверки требований;
* при создании тестов нужно учитывать приоритеты и реальные риски;
* полезно сравнивать разные варианты решения и обосновывать свой выбор;
* при возникновении сложностей рекомендуется обращаться к дополнительным источникам.

Особое внимание уделяется тому, что **требования могут быть сформулированы неоднозначно**. Например, формальное требование может допускать один вариант поведения, тогда как здравый смысл предполагает другой. В такой ситуации необходимо выяснять, что именно имел в виду заказчик. ([studylib.net][1])

# 4.3. Командные файлы для Windows и Linux

В этом подразделе показан пример **автоматизации дымового тестирования** с помощью командных файлов.

Общая последовательность:

1. Очистить результаты предыдущего запуска.
2. Подготовить входные данные.
3. Запустить приложение.
4. Передать приложению тестовые файлы.
5. Дождаться выполнения обработки.
6. Проверить наличие ожидаемых результатов.
7. Проверить отсутствие результатов, которые не должны появиться.
8. Проверить удаление/перемещение исходных файлов.
9. Сравнить полученные файлы с эталонными.
10. Записать результаты проверок в журнал.

В книге приведены примеры скриптов для **Windows CMD** и Linux. ([studylib.net][1])

Главная идея: даже простые командные файлы позволяют автоматизировать повторяющиеся проверки и быстро определить, работает ли основная функциональность приложения.

# 4.4. Пример данных для попарного тестирования

Этот раздел содержит пример набора данных, который можно использовать при выполнении **попарного тестирования**.

Суть попарного тестирования:

> необходимо подобрать набор тестов, обеспечивающий проверку различных пар значений параметров.

Полный перебор всех комбинаций может быть слишком большим. Попарный подход позволяет сократить количество тестов, сохранив проверку взаимодействия параметров попарно.

Например, если приложение имеет несколько параметров:

* ОС;
* браузер;
* версия;
* язык;

то вместо проверки абсолютно всех комбинаций можно сформировать сокращённый набор, покрывающий пары значений.
